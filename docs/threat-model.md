# Threat Model — mcpvet itself

> "An attacker who compromises a security tool compromises everyone who uses it."

This document describes what `mcpvet` can do, what an attacker who controls `mcpvet` (or any of its dependencies) could do, and the mitigations we apply.

## What `mcpvet` does

- Reads MCP config files from well-known filesystem locations (global IDE configs and workspace-local configs)
- Parses JSON, JSONC, and TOML content
- Pattern-matches tool descriptions, commands, args, env vars, headers, and URLs against a curated catalog of malicious patterns
- Optionally calls the npm, PyPI, and GitHub registries to verify server origins
- Reads/writes a local baseline file (`~/.mcpvet/baseline.json` by default)
- Optionally reads `.mcpaudit.yaml` policy files
- Emits output to stdout (human, JSON, SARIF, markdown) and structured logs to stderr

## What `mcpvet` does NOT do

- Does not connect to the target MCP servers. All analysis is static.
- Does not write to any file outside the user's explicit `--baseline-path` or output directory.
- Does not exfiltrate data. No telemetry by default. No outbound calls except the user-enabled origin verification (npm, PyPI, GitHub).
- Does not require any special OS privileges. Runs as a normal user process.
- Does not install, modify, or execute any MCP server.

## Trust boundary

`mcpvet` runs with the same privileges as the user who invokes it. It reads the same files the user can read, and (in `--online` mode) makes outbound HTTPS calls to public registries. It does NOT escalate, sandbox, or modify permissions.

## Attacker model 2: a compromised `mcpvet` dependency

If an attacker controls one of our runtime dependencies (transitively or directly), they can:

| Capability | Risk | Mitigation |
|---|---|---|
| Execute arbitrary code at install time | High | `pnpm.onlyBuiltDependencies` whitelist; lockfile committed; `pnpm install --frozen-lockfile` in CI |
| Execute arbitrary code at runtime | High | Minimal dep tree; no `postinstall`; supply chain via `pnpm audit` gated in CI; Dependabot weekly |
| Read user filesystem (during scan) | High (sensitive) | No telemetry, no exfil, no network calls except user-enabled origin verification |
| Phish via fake update notifications | Medium | We never prompt for updates; the npm CLI handles updates |
| Backdoor the binary via tampered install | High | Reproducible builds (TBD); checksum verification on install (TBD) |

## Attacker model 3: a malicious `mcpvet` release

If an attacker controls a release tag on GitHub or an npm version, they can ship a backdoored `mcpvet` binary to every user who installs or updates.

| Capability | Risk | Mitigation |
|---|---|---|
| Ship a backdoored `mcpvet` on npm | Critical | npm publish gated to CI with trusted publisher; provenance attestations (TBD after first release) |
| Ship a backdoored `mcpvet` via GitHub release | Critical | Releases created only via signed tags; binaries published with SHA-256 (TBD) |
| Ship a backdoored GitHub Action | Critical | Action pinned by SHA in docs; major-version tags protected; no external action references in CI |

## Attacker model 4: a malicious pattern entry

If a contributor adds a malicious pattern to the catalog (e.g. one that flags a legitimate tool as malicious to push users to a competitor), users would be misled.

| Capability | Risk | Mitigation |
|---|---|---|
| False-positive floods that block real work | Medium | All patterns require a public reference (CSA report, OWASP, CVE, incident); code review for any pattern PR; no auto-merge |
| Pattern that matches legitimate traffic as exfiltration | Medium | Severity tuning + whitelist per finding; users can suppress with `<!-- mcpvet:ignore -->` (TBD) |
| Pattern that hides a real attack (e.g. by matching too broadly) | Low | Pattern tests (must match the documented example; must NOT match a list of known-good) |

## Data `mcpvet` touches

| Data | Where it comes from | Where it goes | Sensitivity |
|---|---|---|---|
| MCP config files | User's local FS | In-memory only | High (may contain tokens, paths) |
| Tool descriptions | Same | In-memory, output | High (may contain injected instructions) |
| Environment variables | User's process env | In-memory only when explicitly passed | High (may contain secrets) |
| npm/PyPI/GitHub responses | Public registries | In-memory, output (server name + version + maintainer) | Low (public data) |
| Baseline file | `~/.mcpvet/baseline.json` | That file, plus stdout if requested | Medium (reveals user's MCP surface) |
| Logs | Generated by mcpvet | stderr | Pino configured to redact known secret-shaped values |
| Telemetry | None | Nowhere | n/a |

## Things we explicitly do NOT log by default

- File contents beyond the matched substrings
- Environment variable values (only names, in verbose mode)
- Full URLs from HTTP calls (only hostnames, in verbose mode)
- Any value matching a known secret shape (regex list in `src/cli/logger.ts`, TBD)
